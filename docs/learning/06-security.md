# 第6回：DB・認証・安全対策

目標：データの関連と、ログイン・権限・防御の違いを説明する。

## 基礎と実コード

- [db/schema.sql](../../db/schema.sql)：主キーは行を識別するID、外部キーは別テーブルとの関連。questionsとanswersは一対多。Session・通知・いいねもDB保存する。
- [db/pool.js](../../db/pool.js)：pgの接続プール。アプリ再起動でJSの変数が消えても、PostgreSQLへ保存した行は残る。Previewでは専用 `PREVIEW_DATABASE_URL` を要求する。
- [auth.js](../../auth.js) の `hashPassword`・`verifyPassword`：salt付きscryptでパスワードをハッシュ化・照合する。平文保存や復号して比較する方式ではない。
- 同ファイルの `installAuth`：Cookieのトークンから有効なDB Sessionとユーザーを探し、`req.user` にID・公開名を設定する。DBへはSessionトークンのハッシュを保存する。
- `requireUser` はログイン確認。個別ルートの所有者比較は、その投稿を変更する権限の確認。両者は別の判断。
- [app.js](../../app.js)：SQLの値はプレースホルダーで渡す。EJSの `<%=` はHTMLエスケープする。
- `app.js` のOrigin確認と `auth.js` のCSRFトークン確認：別サイトから意図しない変更を送られることへの対策。
- [rate-limit.js](../../rate-limit.js) と [SECURITY.md](../../SECURITY.md)：頻度制限はDBで共有する。超過は429。操作練習で制限されたら表示された待ち時間を守る。

認証は「誰か」、権限は「何を変更できるか」。入力検証・SQLパラメーター・HTMLエスケープ・CSRF対策は、それぞれ別の問題に対応する。
